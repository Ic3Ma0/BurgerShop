# BurgerShop：给产品 Agent 的交接

更新：2026-09-11。用户已确认 MVP 完成；后续由用户提供方向，产品 Agent 整理 spec，开发 Agent 实现与验证。本文是开发侧提出的协作方式，供产品 Agent 沿用和改进；不代表用户已经批准任何新增功能。

## 你要交付什么

请把用户的想法转成**可观察、可实现、可验收的玩家行为**。每份 spec 聚焦一个可以独立交付的结果，说明本次改变什么、涉及哪些现有功能、做到哪里算完成。

产品侧负责目标、优先级、玩法规则、数值、交互、呈现和验收标准。开发侧负责核对实际代码、技术方案、任务拆分、实现、测试、构建与真机验证。涉及产品体验的技术取舍，开发会说明影响并给出推荐方案；普通实现细节由开发自行决定。

你不需要猜测类名、目录结构、数据库表或具体算法。只有接口兼容、平台或性能等确实影响交付的要求，才应作为技术约束写入 spec。

## 每份 spec 最需要讲清的内容

1. **目标与变化。** 谁在什么场景遇到什么问题？现在怎样，本次之后怎样？避免仅写“更好玩”“更流畅”“优化一下”。
2. **本次范围。** 必须交付的内容、本次明确不做的内容，以及前置依赖。其他想法放入候选清单，不自动加入本次实现。
3. **行为与数值。** 从哪里进入，满足什么条件，玩家做什么，系统何时响应，消耗和产出是多少，界面怎样反馈。数值带单位，并注明是累计值、每次变化还是等级对应值。
4. **相关边界。** 根据功能说明资金不足、空库存、满载、重复触发、中途离开、玩家与员工竞争同一资源等情况。不相关的项目可以省略。
5. **旧进度与生命周期。** 新状态是否保存，老玩家的默认值或解锁条件是什么，后台与重开如何处理。默认保留已有进度；重置、补偿或改变已有权益必须是明确产品决定。
6. **验收。** 给定具体初始状态与操作，写出可观察的结果；区分必须通过的条件和后续调优建议。涉及手机输入、布局、渲染或生命周期时，写出真机操作路径。

使用 [spec 模板](specs/SPEC_TEMPLATE.md)。文字调整可能只需要几行；跨系统功能再增加状态表、流程图或多项验收。文档长度不是质量标准。

## 如何表达规则，减少开发猜测

下面仅是写法示例，**不是本次需求，也不代表已获用户批准**。

模糊表达：“让员工搬得更多，价格合理一点。”

可实现的表达：“已雇佣员工后，进入员工升级区停留 1.5 秒；花 80 金币，将容量从 2 提高到 3，最多购买一次。余额不足不扣款，显示差额；停留未完成就离开时计时归零。升级不会生成额外汉堡，当前携带数量不变，下一次取餐按新容量执行。购买结果需要保存；旧存档默认未升级。”

对应的一条验收可以是：“已雇佣员工、余额 100、未升级；完成一次购买后余额为 20。员工下一次取餐最多携带 3 个，重新打开游戏后容量仍为 3，再次进入不会重复收费。”

示例中的价格、容量、入口与文案仍需产品侧根据用户意图确定。开发不会把模板示例当作待办。

## 不确定项与需求变更

- 将“用户明确要求”“产品建议”“待决定”标清；建议不要包装成用户已经确认的结论。
- 产品侧尽量在交接前消除会改变玩法、经济、存档或交付范围的歧义。需要用户决定时，给出具体选项、影响和推荐，集中处理关键问题。
- 若 spec 已足够明确，用户交付后开发直接开工，不增加例行的二次确认。
- 低影响、可逆的细节可以注明“由开发按现有风格决定”。不因个别次要空缺暂停整个功能；开发记录采用的默认值。
- 对无法安全推断的关键规则，开发一次性列出缺口和推荐处理方式，并继续不受影响的部分。尽量经产品侧整理后由用户决定，减少对用户的零散追问。
- 每份 spec 使用稳定编号和版本，例如 `BS-SPEC-010 v1.0`。改动同一需求时递增版本并列出变更点；后续 spec 引用依赖编号。
- 将开发报告的实际行为、最终数值、已知限制回写到 spec。若与验收标准不一致，应明确标注未满足项或记录经用户同意的调整，不静默修改验收来迁就结果。

## UI、资源与性能需求怎么写

视觉变更请提供适用界面或场景、参考图、希望保留和改变的部分、文案及不同状态；需要时补出布局关系、动画时机和资源清单。说明本次可以继续用占位资源，还是必须交付最终素材。参考图表达目标，不自动表示允许购买或直接复制其素材。

数量增长或性能优化请给出目标场景，例如员工/顾客/设施规模、设备、持续时间和希望改善的现象。已有测量可以直接附上；没有测量时注明未知，由开发先复现和测量，不把猜测写成既有事实。

实现完成后按影响范围验证。文案小改不必重复全套十分钟测试；涉及经营状态、多人竞争同一资源、存档或 Android 渲染的变更，需要相应回归。**成功生成 APK 不等于真机验收通过。**

## 开发侧如何交付给你

开发报告将对应 spec 编号和版本，提供玩家可见变化、实际使用的数值、验收结果、必要截图、构建/安装入口、相关提交或 PR，以及未完成项和已知限制。保存结构变化时会说明旧存档如何处理。

产品侧据此更新功能清单和后续需求，用户负责体验反馈与产品取舍。验收状态与是否合并、是否发布分别记录；功能完成不自动表示获得所有后续发布操作的授权。

## 可直接作为产品 Agent 的工作提示

你负责 BurgerShop 的产品规格。请先阅读本交接和最新开发记录，将用户给出的方向整理为开发 Agent 能直接执行的增量 spec。优先明确玩家目标、功能范围、触发条件、数值与状态变化、界面反馈、相关边界、旧存档兼容以及可复现的验收步骤。将用户已确认事项、你的建议和未定项分开；不要擅自扩展范围或发明当前项目能力。把技术实现细节留给开发，只有确实影响产品结果的约束才需要指定。小需求保持简短，大需求按可以独立交付的结果拆分。开发反馈后同步 spec 的实际结果和后续版本，减少用户在两个 Agent 之间重复解释。
