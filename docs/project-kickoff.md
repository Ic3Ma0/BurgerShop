## 第一版范围建议

核心循环：移动角色 → 取餐和搬运 → 给柜台补货 → 顾客购买 → 收取收入 → 升级设备或雇员 → 提高经营效率。

首版限制在一个店铺、一种主商品、一条售卖动线，包含：

- 移动、相机、基础碰撞与触屏输入。
- 生产、搬运容量、堆叠表现、补货和库存扣减。
- 顾客生成、排队、购买、离场与收款。
- 基础货币、设备升级、一个自动化岗位和店内扩建。
- 本地存档、新手引导、基本音效和操作反馈。
- 可在选定 Android 真机上安装、连续试玩和恢复存档的版本。

先用占位模型验证操作手感与节奏，再统一视觉。第二家店、复杂菜谱、员工个性、多货币、活动、排行榜、账号和云存档进入候选清单。广告和内购作为后期独立交付项，是否进入这轮周期取决于正式发布目标和剩余时间。

## 8–12 周里程碑建议

| 阶段 | 主要工作 | 可检查的结果 |
| --- | --- | --- |
| 第 1 周 | 确认 Unity 工程、建仓准备、需求草案、第一次 PR 流程；尽早检查 Android 构建环境 | 本地工程能打开运行，最小场景能安装到目标手机；协作流程用一个小改动跑通 |
| 第 2–3 周 | 移动、生产、搬运、售卖、收钱、首次升级 | 玩家可以从零完成一次经营循环，并理解升级收益 |
| 第 4–5 周 | 顾客队列、员工自动化、存档、基础数值 | 连续经营不因队列或库存状态卡住，重新启动能恢复进度 |
| 第 6–8 周 | 店内扩建、引导、视觉音效、性能和试玩修正 | 有明确进度目标的 Android 测试版；完成一轮外部试玩 |
| 第 9–10 周 | 根据反馈调整节奏，按范围决定是否接入商业化 | 修复试玩中反复出现的问题；如接广告或内购，完成对应测试环境验证 |
| 第 11–12 周 | 修复、兼容性检查、发布准备和缓冲 | 候选发布版本、已知问题清单、版本说明和可追溯构建 |

如果周期压缩到 8 周，交付目标收敛为第一家店的测试版。如果要求公开上架，应在第 1 周核查开发者账号、测试与审核要求，将商店流程纳入排期；商店批准日期不能仅由开发排期保证。

每周只承诺少量可验收结果。新增需求先放候选清单；影响当前里程碑时，明确替换掉哪项工作或调整哪项交付日期。第 2 周结束后按实际速度重新估算。

## 工具与信息归属

| 工具 | 建议职责 |
| --- | --- |
| Unity Editor | 场景、Prefab、资源导入、运行、调试和手机构建 |
| Codex 桌面端 | 需求讨论、功能实现、问题调查、查看改动和审查 |
| Codex CLI | 终端中的实现、构建脚本、检查和重复操作 |
| Cursor | 阅读代码、手动修改、局部调试与辅助审查 |
| GitHub | 代码和资源版本、具体开发 Issue、PR、检查结果、版本记录 |
| Notion | 产品目标、玩法设计、里程碑、决策记录和试玩反馈；关联对应 Issue/PR |
| Slack | PR 进展、构建失败、版本可试玩等通知，以及临时讨论 |

Codex CLI 可以在终端中检查、修改和运行代码，也支持脚本化工作。[官方 CLI 文档](https://learn.chatgpt.com/docs/codex/cli)

同一工作目录同时只安排一个工具主动修改；需要并行实现独立任务时，使用各自分支和 worktree，集成后统一在 Unity 验证。worktree 提供独立的工作文件，需要先有 Git 仓库；它不能消除后续合并时的逻辑或资源冲突。[官方 worktree 文档](https://learn.chatgpt.com/docs/environments/git-worktrees)

具体开发任务的状态以 GitHub 为准，Notion 保留产品层面的需求与验收，Slack 讨论形成的决定回写到相应记录。避免手动维护三份相同的任务状态。

## 最小联动方案

第一步，选择正式 GitHub 仓库。仓库根目录建议为 `BurgerShop/`，纳入 Assets 及其 `.meta`、Packages 和 ProjectSettings；使用 Unity 适用的忽略规则排除 Library、Temp、Logs 等生成文件。大体积源素材按需配置 Git LFS。建仓前确认文件清单和实际 Unity 版本。

第二步，用一个小功能走完完整流程：需求 → GitHub Issue → 功能分支 → 提交 → Draft PR → 检查和试玩 → 修正 → 合并 → 版本记录。每个 PR 描述玩家可见变化、关联任务、验证方式；涉及画面或玩法时附截图或短录屏。第一版不必增加长期 develop 分支。

第三步，将 GitHub 官方应用连接到指定 Slack 工作区和频道，订阅相关 PR、发布及需要关注的工作流事件。通知范围保持精简。官方集成支持仓库订阅和事件筛选，但需要在实际工作区完成安装、账号连接及权限配置。[GitHub 与 Slack](https://docs.github.com/en/integrations/how-tos/slack/use-github-in-slack)、[通知配置](https://docs.github.com/en/integrations/how-tos/slack/customize-notifications)

第四步，在 Notion 建立项目主页和需求记录，先关联真实 Issue/PR 链接。官方 GitHub 连接还提供同步数据库、PR 关联和状态更新；是否采用这些能力，要以目标工作区的账号、权限和可用功能为准。关联 PR 的合并状态不直接代替需求的试玩验收。[Notion GitHub 连接](https://www.notion.com/help/github)

接通验收：同一个小改动在 GitHub 有提交、PR 和验证记录，在 Notion 能追溯需求，在指定 Slack 频道能看到预期通知。首周为工具联动预留最多 1–2 个工作日，未接通部分列出具体阻塞，继续推进可独立开发的玩法。

## 质量与验收建议

- AI 完成实现后进行单独审查；涉及玩法的改动由用户实际试玩确认。
- 检查重点为金额和库存守恒、队列与员工状态、存档恢复；关键规则适合自动化测试，操作手感依靠试玩。
- CI 逐步加入实际可运行的 Unity 检查。云端 Unity 构建需先确认编辑器版本、运行环境和许可证条件，前期可保留本地构建验证。
- 每周留存一个可试玩版本，记录版本号、对应提交和已知问题。
- 第 8 周建议检查：新玩家无需口头指导完成第一次售卖和升级；连续试玩 15–20 分钟没有阻断问题；重启后恢复进度；在选定目标设备上达到约定的性能目标。
