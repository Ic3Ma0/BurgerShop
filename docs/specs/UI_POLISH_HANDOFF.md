## 默认开发与验证方式（用户确认，2026-09-12）

- 默认以本地 Unity 开发、验证和演示为主；直接编辑代码，普通游戏逻辑优先使用针对性自动化测试。
- 需要检查视觉和交互时，使用 Computer Use 操作 Unity 的 SampleScene Play；画面验收不能只靠代码断言。
- 每批功能完成后集中构建 Android 包，在 vivo 上验证平台差异和关键流程，包括实际触摸/多指、安全区、渲染/声音、生命周期及受影响的存档或性能。
- 不为每次普通逻辑修改反复构建、安装或遥控手机。同批多个 Spec 的重复真机步骤合并执行，将同一证据分别对应到相关 AC。
- 仅在新改动、失败、新平台差异或未解决问题提供理由时重复或扩大测试；没有新证据不重跑已通过项目。
- 达到 Spec 验收标准后及时交付，明确实现版本、证据和未验证项；不无限打磨、不降低标准、不把未执行的验证写成通过。

本轮 026–028 作为一批，先分别完成本地验证，集成后集中构建并执行合并后的 vivo 验收。原有 AC 不降低；涉及同一路径或同一状态的真机证据可复用。

## 范围与完成条件

- 本轮不改经营经济、不新增角色成长系统、店铺等级或广告，也不进行整套 3D 场景和角色重制。因此成品会改善 UI 和动作反馈，但占位模型仍会限制整体美术完成度；模型升级应另列后续任务。
- 保护真实存档、已有本地改动及 _Recovery；不要卸载游戏或清除数据来验证本轮。
- 分别完成 Spec AC、相关 EditMode 测试、SampleScene 可视验证及指定 vivo 验收；真机不可用则明确未验证，不声称通过。
- 提供同一存档/角度的前后对照截图、同一路径的前后操作录像，以及带声音的经营录像。视觉目标必须落实在 Unity 实机，不以静态效果图代替实现。
- 回填实际参数、素材来源、验证结果、APK 路径、未完成项，并分别说明实现/验收/合并/发布状态。UI 审美和主观手感仍需用户体验反馈，自动测试只能验证规则和边界。
