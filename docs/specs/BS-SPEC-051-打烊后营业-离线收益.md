## 1. 目标

玩家关闭游戏再打开时，能看到"**我不在的时候店还在营业**"的具体结果，并因此产生第二天回来的理由。

**可核对**：一名雇满 3 名员工、离线 8 小时的玩家，重新进入时看到一份离线结算，金额落在既定上限内且只发放一次。

---

## 2. 范围

**范围内**

- 存档新增跨会话时间戳，玩家离开时长可被正确计算
- 离线收益按**当前进度**结算（不是固定值），并受封顶约束
- 收益多少**由员工决定**：员工数量与员工速度/携带等级
- 进入游戏时的「打烊结算」面板（复用现有 HUD 风格）
- 系统时间回拨的防御与时长截断
- 存档 v14 → v15 迁移，旧档不掉进度

**非目标（明确不做）**

- ❌ 不做体力系统、不做每日任务与每日重置（那是另一台时钟的另一刀）
- ❌ 不做"看广告翻倍"（本项目当前无广告系统）
- ❌ 不做**离线期间继续生产库存**——离线只产金币，不产汉堡/盒子/零件
- ❌ 不改任何现有价格、升级曲线、等级机制、员工人数上限
- ❌ 不做服务器时间校验（本项目无后端；局限见 §3）

---

## 3. 约束

| 约束 | 违反即不成立 |
| --- | --- |
| **只能给金币** | 离线不得直接改变等级、星数、解锁、设施数量——**推进进度必须在线** |
| **不替代在线** | 单次结算必须**远低于**同时长在线可赚的金额（§4 公式下自动满足，见校验） |
| **不越过当前的墙** | 单次结算 ≤ **当前下一级升级成本 × 8**（由公式结构保证，不是靠额外判断） |
| **0 员工 = 0 收益** | 未雇员工时离线收益必须为 0（这让"第一次雇工"多一个动机） |
| **幂等** | 同一段时间的收益只能领取一次；重启、暂停、切后台都不能重复发放 |
| **不改 042/043** | 不触碰等级门槛、解锁顺序、设施商城与摆放规则 |
| **本地存档的诚实边界** | 无后端时无法完全防篡改；本 spec 只做**回拨检测 + 时长截断**，并在交付记录里写明残余风险 |

## 4. 输入 / 输出

**输入**

- `staffCount`：已雇员工数（0–3）
- `staffSpeedTier` / `staffCarryTier`：员工速度与携带等级（0–20）
- `offlineMinutes`：本次离线分钟数
- `nextUpgradeCost`：当前**最便宜的**可购买升级项的标价
- `lastSeenUtcTicks`：上次存档时的 UTC 时间

**输出（结算公式）**

```
① 员工额度   maxEquivalents = 8 × (staffCount / 3) × (1 + 0.03 × (staffSpeedTier + staffCarryTier)) / 2.2
② 时长系数   timeFactor     = min(offlineMinutes, 480) / 480
③ 结算金额   grant          = nextUpgradeCost × maxEquivalents × timeFactor
```

**这个公式只有两个杠杆，没有装饰性乘数**：

| 情形 | `maxEquivalents` | 离线 8h 结算 |
| --- | --- | --- |
| 0 员工 | **0** | **0** |
| 1 员工，等级 0/0 | **1.21** | 1.2 次升级的等值金币 |
| 3 员工，等级 10/10 | **5.82** | 5.8 次 |
| 3 员工，等级 20/20（满配） | **8.00** | 8 次（上限） |

**为什么用「几次升级的等值」而不是「产出速率」**
按速率建模需要先估算在线收入率（本项目是人工搬运驱动，路径/订单/升级都会影响），既不准也不可测。改成"当前升级成本 × 员工额度"后：**自动跟随进度**（成本本身就是进度的函数）、**天然封顶**、**可被断言**。

## 5. 关键决策点（**已确认，全部按推荐值锁定**）

| # | 决策 | 选项 | ✅ 已确认 |
| --- | --- | --- | --- |
| **D1** | 离线时长上限 | 8h / 12h / 24h | ✅ **8h** —— 手游的典型离线间隔就是"过夜"；12h 以上会让"一天回来两次"失去必要 |
| **D2** | 未雇员工时 | 0 收益 / 基础 20% | ✅ **0 收益** —— 与 I5"改写已有循环"一致：让雇工**多一个价值维度**，而不是并列一个新系统 |

| **D4** | 满配额度 | 6 次 / 8 次 / 12 次 | ✅ **8 次** —— 落在 I6 建议的 6–10 区间中段 |

## 6. 验收标准

| 编号 | 初始状态 | 操作 | 必须出现的结果 |
| --- | --- | --- | --- |
| **AC-01** | 全新档，首次进入 | 直接退出再进入 | **不产生**离线收益；存档已写入时间戳 |
| **AC-02** | 3 员工、等级 10/10 | 模拟离线 8 小时 → 重开 | 结算 = `下一级成本 × 5.82`，误差 ≤ 1 金币；面板显示离开时长 |
| **AC-03** | 0 员工的档 | 模拟离线 8 小时 | 收益 **= 0**，面板显示"雇一名员工，打烊后才有收入" |
| **AC-04** | 3 员工、等级 20/20 | 模拟离线 8 小时 | `maxEquivalents` **= 8.00**（精确等于上限，不超出） |
| **AC-05** | 任意档 | 把系统时间**回拨** 1 天后再进入 | 收益 **= 0**；不报错；时间戳重置为当前时间；后续恢复正常结算 |
| **AC-06** | 任意档 | 模拟离线 **30 天** | 按 **8 小时**截断（`timeFactor = 1`），不是 30 天 |
| **AC-07** | 任意档 | 模拟离线 **10 分钟** | 结算 = `下一级成本 × maxEquivalents × 0.021`（按时长等比例，不是拿满） |
| **AC-08** | 任意档 | 遍历多个进度点 | 结算金额**恒 ≤ 下一级升级成本 × 8**（断言，无例外） |
| **AC-09** | 任意档 | 遍历多个进度点 | 结算金额恒 **&lt; 同时长在线可赚金额**（用既有在线结算做对照断言） |
| **AC-10** | 领取结算后 | 检查所有进度状态 | 只有金币变化；等级、星数、解锁、设施数量、员工数**全部不变** |
| **AC-11** | v14 旧档 | 读档 → 游玩 → 退出 → 重开 | 首次读档**不产生**收益；第二次开始正常；金币与既有进度不丢 |
| **AC-12** | 已产生未领取的结算 | 强制结束进程后重开 | 不能重复领取；已领取的金额不因重启再发一次 |
| **AC-13** | 本刀 PR | 查看 diff | 未新增广告/内购/体力/每日任务；未改任何价格与升级曲线；存档 schema 仅新增离线相关字段 |

**不应破坏的既有行为**：042 的双门槛与循环等级、043 的商城与摆放、全部既有价格与产能公式、存档 v1–v14 的兼容校验与校验和格式。

## 7. 变更记录

- v1.0：首次规格（采用"产出速率 × 效率"建模）。
- v1.1：**改掉 v1.0 的一处设计缺陷**。v1.0 用 `产出速率 × 效率` 再叠加"8 次升级"封顶，实测（Python 复算）显示**封顶在所有场景都先触发**，导致效率系数与员工等级是**装饰性参数**——正是本项目已经吃过亏的"数字会变但不影响任何决定"模式。v1.1 改为**单一杠杆**：员工直接决定"能拿几次升级的等值"，时长按比例折算，封顶由公式结构保证而非额外判断。
- v1.2：**D1–D4 经用户确认，全部按推荐值冻结**；状态转「可开发」。
- v1.3：编号由 046 更正为 **051**（046 已被「门前动线与汽车服务区」占用并交付）。内容未变。
- 设计依据：Cookie Clicker 移动版（离线模型整条重做 + 本地时间漏洞）、My Perfect Hotel（陡成本 + 按比例授予）、Kingshot（AFK 箱 12h 上限）、Eatventure（3h 基础 → 32h 沙漏）。详见 `core-research/SYNTHESIS.md` §4 第 4 项。
