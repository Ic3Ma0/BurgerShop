## 技术边界与方案审查（改运行时代码时填写）

开发前先读实际调用方和已有模块，再填写；小修可用五行，不新增用户审批步骤。不是类名清单，也不要求每次新建模块。

- 归属与复用：放在哪个已有模块、复用哪个入口；若需局部重构，原来的哪两种职责必须分开，为什么？
- 状态归属：每个变化状态的唯一所有者是谁；其他模块如何读取/请求修改；是否避免重复持有或多处写入？
- 依赖方向：谁调用谁；规则、场景、显示、存储的边界；本次明确禁止哪些反向依赖？
- 兼容与失败：旧存档/旧调用方如何保持；取消、保存失败或重复操作时由谁回滚/重试？
- 自动防线：哪项行为测试或依赖检查会在边界被破坏时失败；运行 `bash scripts/check-boundaries.sh --spec <本规格路径>`。脚本只检查约定存在与具体依赖，方案合理性仍需结合代码审查。
